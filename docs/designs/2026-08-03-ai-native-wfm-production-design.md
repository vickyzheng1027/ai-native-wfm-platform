# AI Native WFM 真实系统改造设计文档

## 背景

现有 `ai-native-wfm-platform` 已具备 Node.js、SQLite、登录权限和部分真实业务 API，但其前端没有采用 `ai-native-wfm` 已完成的运营中枢、门店排班台和员工端页面，线上体验仍接近功能拼装。`ai-native-wfm` 的页面交互完整，但业务状态、金额、覆盖率和 Agent 过程主要由浏览器内存与固定脚本驱动，不能作为真实系统使用。

本次改造不创建新项目。所有实现继续落在 `ai-native-wfm-platform`，直接迁移 `ai-native-wfm` 的 UI 页面，在现有后端上补齐 PostgreSQL、OpenAI Agent、统计预测、规则知识库、决策反馈和复盘进化能力。

## 目标

1. 直接使用 `ai-native-wfm` 的 `home.html`、`operations-hub.html`、`index.html` 和 `employee.html` 页面结构与视觉交互。
2. 删除固定延时、固定数组和固定业务数字，所有页面数据由后端 API 和数据库提供。
3. 使用 OpenAI API 实现真实 Agent，负责自然语言理解、上下文收集、工具编排和结果解释。
4. 使用可复算统计引擎预测客流与人力需求；LLM 不直接生成预测数字。
5. 合规、排班、工时、假期、账户、薪资和人效由确定性引擎计算。
6. 所有写操作经过人工确认、版本复核、事务提交和审计。
7. PostgreSQL 保存业务数据、规则版本、预测版本、Agent 轨迹和反哺记录。
8. 沿用当前 GitHub 仓库和 Render 服务完成部署。

## 方案设计

### 1. 现有项目内分层

- `public/`：迁入四个现有 UI 页面和对应脚本，页面只负责展示、表单输入和确认动作。
- API 层：沿用原生 Node.js HTTP 服务，补充统一路由、Schema 校验、错误码和请求幂等。
- Agent 编排层：OpenAI Agent 生成结构化意图并调用白名单工具，记录每一步状态、输入摘要、输出摘要和耗时。
- 预测层：基于历史客流、销售、活动类型、星期和历史偏差执行加权移动平均与趋势修正，输出预测值、区间、版本和特征依据。
- 确定性领域层：负责候选方案、合规、影响模拟、自愈调班、工时、成本、账户、薪资和人效。
- 数据访问层：从当前 SQLite 访问方式逐步抽离为仓储接口，生产使用 PostgreSQL，本地测试保留 SQLite 适配器。

### 2. AI 边界

Agent 可执行：

- 抽取门店、日期、经营目标、预算、覆盖率、员工偏好和账户要求。
- 调用工具读取员工、排班、考勤、假期、规则、账户和经营历史。
- 调用预测、排班、合规和影响模拟工具。
- 基于确定性结果生成可解释说明。

Agent 禁止执行：

- 直接判定合规通过。
- 直接计算工时、工资和账户金额。
- 绕过确认写入数据库。
- 修改已生效的硬约束规则。

Agent 输出必须通过 JSON Schema 校验。模型超时、输出非法或缺少关键字段时，返回可恢复状态并只追问一个必要问题。

### 3. 数据模型

沿用现有员工、门店、用户、班次、申请、考勤、工时、工时银行、劳动力账户、成本分摊、薪资、反馈和审计表，新增：

- `demand_forecasts`：预测范围、特征、算法、预测值、置信区间、偏差和版本。
- `compliance_rules`：规则分类、适用范围、表达式、来源、严重度、版本和生效状态。
- `agent_runs`：Agent 运行目标、状态、模型、确认状态、数据版本和耗时。
- `agent_steps`：状态机步骤、工具、输入输出摘要和错误。
- `decision_feedback`：采纳、修改、否决、原因和策略权重变化。
- `business_outcomes`：实际客流、销售、成本、覆盖率和数据可信度。
- `strategy_versions`：软偏好权重、来源、版本、生效状态和回滚关系。

所有业务表包含 `tenant_id`、创建时间和必要的数据版本字段。敏感 Agent 输入不保存完整原文，只保留审计所需摘要。

### 4. 页面改造

- `home.html`：真实会话登录与角色入口。
- `operations-hub.html`：活动前、活动中、活动后三阶段；展示真实 Agent 状态机、工具步骤、三候选方案、影响模拟、确认执行、实际结算和三层反哺。
- `index.html`：真实周需求预测、班次、合规风险、方案解释、自愈调班和复盘迭代。
- `employee.html`：自然语言查班、请假、换班、补卡、加班、打卡和偏好登记；写操作均要求员工确认。

保留原 UI 布局和盖雅绿设计规范，移除页面内 `seedScenario()`、固定黄金数字和用 `setTimeout` 伪造的 Agent 步骤。加载、失败、空状态、数据冲突和模型不可用均提供明确界面反馈。

### 5. 核心接口

- `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/me`
- `GET /api/operations/context`
- `POST /api/agent/runs`
- `GET /api/agent/runs/:id`
- `POST /api/agent/runs/:id/confirm`
- `POST /api/agent/runs/:id/reject`
- `POST /api/forecasts/run`
- `GET /api/forecasts`
- `GET /api/compliance/rules`
- `POST /api/compliance/rules/:id/shadow-run`
- `GET/POST /api/employee/commands`
- `POST /api/events/:id/close`
- `POST /api/events/:id/review`
- `POST /api/admin/demo-reset`

现有人员、排班、申请、考勤、账户、薪资和审计接口保持兼容。

### 6. 关键业务流

经理输入经营目标后，后端创建 `agent_run`，Agent 解析目标并调用上下文工具。统计引擎生成需求预测，确定性引擎生成三种候选方案并执行多点合规校验。前端展示方案数字、证据和风险，经理确认后，后端按最新数据版本重新校验并事务写入班次、预计工时、账户归属和通知。

活动中，考勤、补卡、请假和加班事件更新实际状态，缺勤事件生成自愈建议而不静默换人。活动后，系统根据计划与实际计算工时、账户、薪资预估、人效和偏差归因。可信数据生成经营模型、员工画像和策略偏好三层反哺；低可信数据进入人工复核，不更新策略。

## 技术选型

- 前端：复用现有原生 HTML/CSS/JavaScript，避免改变管理层已认可的界面。
- 后端：现有 Node.js 原生 HTTP 服务，按领域拆分模块。
- AI：OpenAI API，使用结构化输出和工具调用；密钥仅来自环境变量。
- 预测：确定性统计算法，保存特征、版本和置信区间。
- 数据库：生产 PostgreSQL，本地测试 SQLite；通过仓储接口隔离差异。
- 部署：现有 GitHub 仓库与 Render Web Service，增加 PostgreSQL 和环境变量。

## 实施计划

1. 建立数据库仓储接口和新增实体迁移，保持现有测试通过。
2. 实现统计预测服务、规则知识库和多点合规校验。
3. 实现 OpenAI Agent Adapter、工具注册、结构校验、状态持久化和确定性兜底。
4. 迁移四个 UI 页面到 `public/`，逐一替换内存数据和固定动画。
5. 实现管理端确认执行、员工命令、活动结算和复盘反哺。
6. 增加单元、契约、API 和端到端测试，覆盖模型异常和数据版本冲突。
7. 配置 PostgreSQL 与 OpenAI 环境变量，推送并在现有 Render 服务重新部署。
8. 验证经理端与员工端完整链路，保留演示租户初始化和经理审计式重置能力。

## 验收标准

- 页面不再读取固定业务数组或固定黄金数字。
- 同一数据库输入可重复得到相同工时、成本、账户、薪资和合规结论。
- Agent 运行可查看真实模型名称、状态步骤、工具调用和失败原因。
- Agent 不可绕过确认写数据，确认时数据版本变化会阻止执行。
- 预测结果包含版本、输入特征、置信区间和可复算证据。
- 管理端和员工端的主要操作均改变数据库状态并可从刷新后的页面验证。
- OpenAI 不可用时，确定性查询与计算功能仍可使用，Agent 功能明确显示不可用。
- PostgreSQL 重启和 Render 重新部署后业务数据不丢失。

## 风险和挑战

- OpenAI Key、模型限额或网络不可用：提供明确降级状态，禁止用模拟结果冒充模型调用。
- SQLite 到 PostgreSQL 的 SQL 差异：使用仓储接口和双适配测试，逐模块迁移。
- 原前端脚本与 DOM 强耦合：保留页面结构，按业务流程分批替换脚本并增加 DOM 测试。
- 规则错误造成合规风险：演示规则必须标注，硬规则只能经版本审批、影子运行和灰度生效。
- 预测数据不足：展示置信区间和数据质量，不把低样本结果描述为高可信预测。
- Render 外部服务可能产生费用：创建或升级付费资源前必须取得用户明确确认。
