# AI Native 排班闭环扩展设计文档

## 背景

当前系统已经具备规则配置、规则库、跨店缺口推荐、合规复核、成本分摊和规则优化闭环，但员工、请假、业务日历、业务需求与正式班表缺少可维护入口。管理者无法从真实人员可用性和既有班次出发生成整周排班，也无法在确认后查看或微调班表。

本次扩展以一条可运行的端到端链路贯穿员工、请假、日历、业务需求、智能排班、正式班表、规则校验、成本与数据反哺。AI 负责理解和解释，确定性代码负责约束、计算和写入，确保比赛演示稳定且结果可复算。

## 目标

1. 提供员工查看、新增和维护能力，覆盖门店、技能、跨店资格、合同工时、成本和排班偏好。
2. 支持员工提交、撤销请假，主管审批和后台补录；已批准请假形成排班不可用时段。
3. 默认按周展示业务日历，可切换前后周，内置中国大陆全年法定节假日和调休工作日。
4. 支持结构化周业务需求和自然语言经营目标两种输入方式。
5. 排班 Agent 结合员工、请假、已有班次、累计工时、日历和当前规则生成三套可执行方案。
6. 客户确认方案后生成正式班表，支持手动新增、编辑和删除班次。
7. 手动调整时硬规则禁止保存；软规则填写原因后可保存，并记录完整审计。
8. 班表执行和调整结果进入规则优化指标，实现数据反哺。

## 方案设计

### 1. 总体架构

系统新增员工管理、请假管理、业务日历、业务需求、智能排班和班表管理六个业务入口，并与现有规则库、合规成本和规则优化共用 SQLite 数据库与确定性规则引擎。

核心业务链如下：

```text
结构化周需求 / 自然语言经营目标
              ↓
       结构化需求人工确认
              ↓
员工 + 请假 + 日历 + 已有班次 + 工时 + 规则版本
              ↓
          排班约束引擎
              ↓
综合最优 / 成本优先 / 员工体验优先
              ↓
          主管选择确认
              ↓
            正式班表
              ↓
      手动微调 + 实时规则校验
              ↓
       成本、审计和规则优化反哺
```

### 2. Agent 与确定性引擎边界

AI Agent 只承担：

- 将自然语言经营目标转换成日期、时段、岗位、预测客流、销售额和需求人数。
- 基于确定性引擎输出的数据解释三套方案差异、风险和推荐依据。

确定性代码承担：

- 元数据校验和防幻觉。
- 已批准请假、不可用时间和既有班次冲突过滤。
- 技能、跨店资格、工时上限、连续工作天数和最小休息间隔校验。
- 候选班次构建、覆盖率、成本、工时均衡和偏好评分。
- 三套方案生成、最新数据二次校验和正式班次写入。
- 手动调整的硬规则拦截、软规则提示、成本更新和审计记录。

模型调用继续使用公司 Gaia Responses API。10 秒超时后重试一次，仍失败则使用明确标识的确定性需求解析，不影响结构化输入和排班计算。

### 3. 数据模型

在现有 `stores`、`employees`、`rules` 和规则版本表基础上新增或扩展：

- `employees`：增加合同工时、联系方式、岗位、状态等可维护字段。
- `employee_availability`：员工固定可用时段和排班偏好。
- `leave_requests`：员工、请假类型、起止时间、状态、申请原因和审批信息。
- `calendar_days`：日期、日期类型、节日名称、是否工作日和调休说明。
- `business_demands`：门店、日期、时段、岗位、预测客流、销售额和需求人数。
- `schedule_plans`：方案类型、规则快照、数据快照版本、指标、状态和生成说明。
- `schedule_plan_shifts`：候选方案内的员工班次、分数与选择依据。
- `shifts`：主管确认后的正式班次。
- `shift_adjustments`：调整前后数据、冲突、操作原因、操作人和时间。
- `rule_validation_logs`：校验对象、规则版本、等级、结果和业务说明。

只有 `approved` 状态的请假进入不可用时段。候选方案保存生成时的员工、请假、班次和规则快照；确认前按最新数据复核，发现变化则标记方案过期并要求重新生成。

### 4. 排班算法

引擎按需求日期、时段和岗位逐项构建候选员工池，依次执行：

1. 员工在职且可用。
2. 具备目标岗位技能。
3. 不与已批准请假冲突。
4. 不与已有正式班次或候选班次重叠。
5. 满足跨店资格。
6. 调整后不超过工时上限。
7. 满足连续工作天数与最小休息间隔。

硬约束通过后，根据覆盖贡献、普通工时、加班成本、交通成本、员工偏好、连续工作天数和工时均衡计算候选分数。三套方案共用候选池，使用不同权重：

- 综合最优：均衡覆盖率、成本、工时公平和员工偏好。
- 成本优先：提高普通工时权重，降低加班、跨店和交通成本。
- 员工体验优先：提高偏好匹配、休息间隔和工时均衡权重。

每套方案返回需求覆盖率、未覆盖时段、总工时、预计成本、跨店人数、软规则风险和具体班次。无法满足的需求必须保留为真实缺口并说明原因。

### 5. 页面与交互

侧边栏调整为：业务总览、员工管理、请假管理、业务日历、业务需求、智能排班、班表管理、规则库、合规成本。

- 员工管理：高密度列表与编辑抽屉，支持查看、新增和编辑。
- 请假管理：员工申请入口、主管审批列表和主管补录入口。
- 业务日历：默认周视图，标识工作日、周末、法定节假日和调休工作日。
- 业务需求：自然语言与结构化周计划使用分段控件切换，解析后必须人工确认。
- 智能排班：输入业务、确认需求、对比方案三阶段；方案指标可比较，具体班次可切换查看。
- 班表管理：按员工和日期展示周班表，班次块显示时间、岗位和门店；通过抽屉新增或编辑。

页面遵循公司 UI 规范：盖雅绿主题、固定顶部导航和侧边栏、4px 间距体系、Lucide 图标、B 端高信息密度、站内对话框与提示、键盘焦点和 ARIA 标签。排班页基于 `schedule-page-template.html` 修改，列表页基于 `list-page-template.html` 的规范模式扩展到同一单页应用。

### 6. 手动调整规则

手动新增、编辑或删除班次必须先调用预校验接口：

- 硬规则：已批准请假冲突、班次重叠、技能不匹配、工时硬上限、最小休息间隔等。失败时禁止保存。
- 软规则：员工偏好、目标成本、跨店距离和工时均衡等。主管填写原因后允许保存。

正式保存使用事务，同时更新班次、员工实时工时、成本指标、规则校验日志和调整审计。审计记录包含调整前后内容、触发规则、规则版本、操作人、原因和时间。

### 7. API 设计

员工与可用性：

- `GET /api/employees`
- `POST /api/employees`
- `PUT /api/employees/:id`
- `GET /api/employees/:id/workload`
- `PUT /api/employees/:id/availability`

请假与日历：

- `GET /api/leaves`
- `POST /api/leaves`
- `POST /api/leaves/:id/approve`
- `POST /api/leaves/:id/reject`
- `POST /api/leaves/:id/cancel`
- `GET /api/calendar?start=&end=`

业务需求与排班：

- `GET /api/demands?start=&end=&storeId=`
- `POST /api/demands`
- `PUT /api/demands/:id`
- `DELETE /api/demands/:id`
- `POST /api/demands/parse`
- `POST /api/schedule-plans/generate`
- `GET /api/schedule-plans/:id`
- `POST /api/schedule-plans/:id/confirm`

正式班表与调整：

- `GET /api/shifts?start=&end=&storeId=`
- `POST /api/shifts/validate`
- `POST /api/shifts`
- `PUT /api/shifts/:id`
- `DELETE /api/shifts/:id`
- `GET /api/shift-adjustments`

### 8. 异常处理

- 模型不可用：明确显示确定性兜底，不伪装成 AI 调用成功。
- 需求无法完全覆盖：返回部分方案和真实缺口原因。
- 候选方案数据过期：禁止确认并引导重新生成。
- 硬规则冲突：返回规则名称、员工、冲突时间和可操作建议，不写数据库。
- 软规则冲突：要求主管输入原因后再次提交。
- 数据写入失败：事务整体回滚，不产生半成品班表或错误工时。

## 技术选型

- 前端：原生 HTML、CSS 和 JavaScript，延续现有单页工作台。
- 后端：Node.js 原生 HTTP 服务。
- 数据库：Node.js 内置 SQLite，使用版本化迁移和事务。
- AI：公司 Gaia OpenAI 兼容 Responses API。
- 排班：确定性约束过滤与多目标评分引擎，不让模型生成工时、成本或合规结论。
- 日历：中国大陆法定节假日和调休数据随演示种子写入数据库，并通过接口查询。

选择该方案的原因是它能在比赛 MVP 时间窗口内提供真实、稳定、可解释的业务闭环，同时保留后续替换为整数规划求解器的边界。

## 实施计划

1. 数据库迁移：扩展员工，新增请假、日历、需求、方案、班次和调整日志表。
2. 确定性领域引擎：实现时间冲突、请假、技能、工时、休息间隔和多目标评分。
3. Agent 编排：实现自然语言需求解析、元数据防幻觉和方案解释。
4. API：完成员工、请假、日历、需求、方案、正式班表和校验接口。
5. UI：基于公司模板实现员工、请假、日历、业务需求、方案对比和周班表。
6. 测试：覆盖规则边界、三方案差异、数据过期、硬软规则和事务回滚。
7. 浏览器验收：完成桌面与移动视口、全量点击、控制台和关键截图检查。
8. 提交部署：推送现有仓库，触发 Render 并验证线上完整链路。

## 风险和挑战

- 24 小时 MVP 无法覆盖大型企业排班的全部约束。本次通过清晰的规则接口和评分权重保留扩展空间。
- 法定节假日政策按年度变化，演示数据需明确年份；正式产品应接入可维护的企业日历源。
- 三套方案是满足约束后的多目标近似最优，不宣称数学全局最优。
- SQLite 适合比赛和单实例演示；多实例正式环境需要迁移到 PostgreSQL。
- Render 免费实例使用临时文件系统，重启后演示数据会恢复；正式持久化需挂载磁盘或托管数据库。

## 验收流程

1. 新增或编辑员工技能、跨店资格、合同工时和偏好。
2. 员工提交请假，主管审批通过。
3. 查看当前周日历中的工作日、周末、节假日和调休工作日。
4. 分别通过结构化周计划和自然语言生成业务需求。
5. 主管确认结构化需求，生成三套排班方案。
6. 验证已批准请假员工不会出现在冲突班次中。
7. 对比三套方案的覆盖率、成本、工时均衡和软规则风险。
8. 确认方案并查看正式周班表。
9. 手动制造请假或工时硬冲突，验证系统禁止保存。
10. 制造偏好软冲突，填写原因后保存并查看审计记录。
11. 验证正式班次、员工工时、成本指标和规则优化数据同步更新。
12. 一键重置并重新完成整条比赛演示链路。
