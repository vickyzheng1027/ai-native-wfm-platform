# 零售连锁跨店调剂智能体系统设计文档

## 背景

本项目用于公司内部 AI 创新比赛，需要在现有 `ai-native-wfm-platform` 项目名称、目录和 Render 部署入口不变的前提下，完全替换原有全模块 WFM 运营中枢，重构为聚焦“零售连锁跨门店人力调剂”的可运行 MVP。

系统需要证明 AI 不只是传统表单的输入助手，而是能在真实业务数据和确定性规则约束下完成规则理解、候选推荐、解释、校验、反馈和规则优化的协作主体。比赛现场需要稳定跑通完整闭环，并清楚区分真实大模型能力与确定性业务计算。

## 目标

1. 运行一条完整业务链：配置规则、提交缺口、生成推荐、合规成本校验、确认调剂。
2. 自然语言规则解析与推荐理由生成真实调用公司 Gaia Responses API。
3. 人员过滤、工时、风险、合规、成本由确定性代码实时计算。
4. 规则变化导致原建议失效时，系统自动触发重新推荐。
5. 将规则沉淀到版本化规则库，并依据排班和调剂结果生成优化建议。
6. 所有数据真实写入 SQLite，支持追溯和一键恢复比赛初始数据。
7. 页面符合公司 UI 规范，业务信息清晰，不直接展示难懂的工具调用或技术状态。

## 范围

### 包含

- 无登录的比赛工作台
- 自然语言规则解析及人工确认
- 业务规则和合规规则的版本化规则库
- 门店缺口提交与确定性候选过滤
- 大模型生成推荐理由及代码校验
- 最新规则二次合规校验
- 跨门店成本拆分
- 校验失败后自动重新推荐
- 基于排班与调剂结果的规则优化建议
- 一键重置比赛数据
- Gaia Responses API 与明确标识的故障兜底

### 不包含

- 登录、权限、多租户
- 客户真实生产数据接入
- 通用排班优化算法
- 假期、时间银行、薪资等其他 WFM 模块
- 规则自动生效；所有规则及优化建议必须人工确认

## 方案设计

### 总体架构

采用原生 Web + Node.js + SQLite 的轻量架构，保留现有项目目录、Node 启动方式、Render 部署骨架和公司模型网关接入，删除并重写旧页面、旧业务接口和旧数据模型。

系统由四层组成：

1. **业务工作台**：规则配置、规则库、缺口推荐、合规成本四个入口。
2. **Agent 编排层**：规则配置 Agent、补位排班 Agent、合规成本 Agent。
3. **确定性引擎层**：元数据校验、候选过滤、风险计算、合规校验、成本拆分、优化指标分析。
4. **数据与集成层**：SQLite 业务数据、版本化规则库、Agent 轨迹、Gaia Responses API。

### 三 Agent 协作

#### 规则配置 Agent

- 将自然语言解析为四类结构化规则。
- 依据真实门店与技能元数据校验模型输出。
- 低置信度或引用不存在元数据时强制标为待确认。
- 人工确认后生成不可变规则版本。
- 定期分析排班、缺口、过滤和校验结果，生成规则优化建议。

#### 补位排班 Agent

- 接收门店缺口事件。
- 调用确定性过滤引擎筛选符合技能、资质、工时、连续工作天数要求的员工。
- 按工时余量排序并取前三名。
- 调用大模型生成面向店长的推荐理由。
- 服务端覆盖模型风险等级并核对理由中的数字。

#### 合规成本 Agent

- 管理者确认候选人后按最新规则版本重新校验。
- 校验员工月工时、连续工作天数和调出门店最低在岗人数。
- 校验通过后创建调剂记录和成本拆分。
- 校验失败后排除失败候选人，将缺口重置为待推荐并自动重新生成建议。

### 规则库与优化闭环

规则库包含两类规则：

- 排班业务规则：最低在岗人数、技能要求、跨店资格。
- 排班合规规则：员工月度工时上限、连续工作天数上限。

每条规则包含主记录和不可变版本。推荐、校验和调剂均保存所使用的规则版本，保证结果可追溯。

规则优化任务定期聚合以下真实数据：

- 技能或资质导致的候选过滤次数
- 候选集为空次数
- 合规校验失败次数及规则类型
- 各门店缺口频率和技能分布
- 调剂员工工时风险分布
- 建议采纳率和人工拒绝原因

优化建议必须包含统计周期、样本量、证据、影响范围、建议修改值和风险说明。建议只能由管理者采纳，采纳后进入规则变更确认并生成新版本。MVP 同时提供“立即运行优化分析”入口，确保现场可演示。

## 页面设计

实现阶段必须使用 `gaia-ui-prototype-generator` 的公司 UI 规范，并读取：

- `specs/design-foundation.md`
- `specs/components.md`
- `specs/layout-system.md`
- `specs/accessibility.md`
- `ICON-LIBRARY.md`
- 一个工作台主模板

必须采用盖雅绿主色、4px 间距体系、Lucide 图标、清晰焦点态和可访问语义。页面保持 B 端高信息密度，禁止营销式大卡片堆叠和浏览器原生弹窗。

### 规则配置台

- 默认首页，顶部展示活动、当前规则版本和闭环状态。
- 自然语言输入支持一次输入多条规则。
- 解析结果展示规则名称、结构化取值、置信度、原文依据和状态。
- 待确认规则直接提供编辑入口，不自动填充不存在的门店或技能。
- 确认后生成规则版本并即时供其他 Agent 使用。

### 规则库

- 表格展示规则名称、类型、适用范围、当前值、版本、状态、命中次数和更新时间。
- 支持查看版本历史、来源原文、执行记录和计算影响。
- 页面包含规则优化建议区，展示证据、建议值、风险及采纳/拒绝操作。

### 门店缺口与推荐看板

- 紧凑表单提交门店、日期、班次、技能、人数和原因。
- 用业务语言展示筛选过程，例如“检查 12 人，排除 7 人，剩余 3 人”。
- 候选表格展示门店、技能、当前工时、调剂后工时、余量、连续工作天数、风险和推荐理由。
- 允许单选候选人并进入确认校验。

### 合规成本详情

- 展示当前使用的最新规则版本。
- 展示员工工时、连续工作天数、调出门店最低在岗人数三项校验。
- 展示调剂时长、员工时薪和成本转移公式。
- 校验失败时说明冲突规则，并展示自动重新推荐结果。

### 信息表达原则

默认只展示管理者需要理解和决策的信息。技术轨迹转换为业务步骤：

- 已识别多少条规则，多少条待确认
- 已检查多少名员工，各类原因排除多少人
- 推荐人数和风险分布
- 使用哪个规则版本进行校验
- 成本如何由工时与时薪计算

Agent 工具调用、原始 JSON 和数据库字段只能放在可展开的“技术详情”区域，不进入主视图。

## 数据模型

### stores

门店编号、名称、区域及可选月度工时预算。

### employees

员工编号、姓名、所属门店、技能、跨店资格、月度已用工时、连续工作天数和时薪。

### rules / rule_versions

规则主记录保存当前版本引用；版本记录保存规则类型、结构化值、来源文本、状态、置信度、生效时间和创建方式。

### rule_drafts

保存自然语言输入、解析结果、未识别内容、大模型运行状态和人工修正结果。

### shortage_events

保存缺口门店、日期、班次、技能、人数、原因、状态和重推荐次数。

### transfer_suggestions

保存候选员工、调剂后工时、风险、推荐理由、所用规则版本、筛选快照和状态。

### transfer_orders

保存最终候选人、调出/调入门店、时长、执行状态和确认时间。

### compliance_checks / cost_allocations

分别保存每项校验的输入、阈值、结果和证据，以及成本金额、费率、工时、归属门店和计算公式。

### rule_optimization_suggestions

保存统计周期、证据指标、规则引用、当前值、建议值、理由、风险、状态和采纳结果。

### agent_runs / agent_steps

保存 Agent 类型、业务对象、模型、运行模式、耗时、重试、兜底状态和业务化步骤摘要。

## 接口设计

### 元数据与工作台

- `GET /api/dashboard`
- `GET /api/metadata`
- `POST /api/demo/reset`

### 规则配置与规则库

- `POST /api/rules/parse`
- `PUT /api/rule-drafts/:id/rules/:ruleId`
- `POST /api/rule-drafts/:id/activate`
- `GET /api/rules`
- `GET /api/rules/:id/versions`

### 规则优化

- `POST /api/rule-optimizations/run`
- `GET /api/rule-optimizations`
- `POST /api/rule-optimizations/:id/accept`
- `POST /api/rule-optimizations/:id/reject`

### 缺口、推荐和调剂

- `POST /api/shortages`
- `GET /api/shortages`
- `POST /api/shortages/:id/recommend`
- `GET /api/shortages/:id/suggestions`
- `POST /api/suggestions/:id/confirm`
- `GET /api/transfers/:id/validation`

接口统一返回业务状态、可读摘要、数据证据和下一步动作。主接口不返回难懂的内部状态码作为页面文案。

## 真实 AI 与确定性计算边界

### 真实大模型

- 规则自然语言解析
- 候选人推荐理由生成

### 确定性代码

- 门店与技能元数据校验
- 置信度阈值覆盖
- 候选资格过滤
- 风险等级计算
- 推荐理由数字一致性校验
- 二次合规校验
- 成本拆分
- 规则优化指标计算

规则优化建议的证据和建议值由代码基于真实统计生成，大模型仅可用于润色解释，不得改变数字。

## 错误处理与兜底

- 大模型调用超时 10 秒。
- 调用失败或 JSON 无效时重试一次。
- 规则解析仍失败时生成确定性草稿，全部标为待确认。
- 推荐理由仍失败时使用代码拼接的真实数据说明。
- 页面必须明确显示“AI 服务波动，当前为兜底结果”。
- 兜底结果不得标记为真实模型输出。
- 候选集为空时明确提示人工协调，不推荐不合规员工。
- 所有写操作使用站内确认弹窗和轻提示，不使用浏览器原生弹窗。

## Demo 数据与重置

预置 A、B、C 三家门店，每店 4 至 5 名员工。B、C 门店员工数据需覆盖：

- 技能匹配且工时余量充足
- 技能匹配但接近月度上限
- 已超过工时条件
- 连续工作天数临界
- 无跨店资格
- 技能不匹配

一键重置需要在单一事务中清理规则草稿、规则版本、缺口、推荐、调剂、校验、成本、优化建议和 Agent 记录，然后恢复固定初始数据，并记录重置时间。

## 测试策略

1. 规则解析结构校验和不存在元数据防幻觉测试。
2. 置信度小于 0.6 强制待确认测试。
3. 候选技能、资质、工时、连续天数过滤测试。
4. 风险阈值及推荐理由数字一致性测试。
5. 最新规则二次校验测试。
6. 规则变化导致原建议失败并自动重新推荐的闭环测试。
7. 成本拆分稳定性与可追溯测试。
8. 规则优化指标、采纳和版本生成测试。
9. Gaia Responses API 超时、重试和兜底测试。
10. 一键重置幂等性测试。
11. HTTP 端到端测试。
12. 浏览器真实点击、桌面与移动截图、控制台错误和布局检查。

## 验收流程

1. 一键重置比赛数据。
2. 输入包含四类规则的自然语言并真实解析。
3. 验证不存在的 D 门店被标为待确认。
4. 修正并激活规则，生成新版本。
5. A 门店提交收银岗缺 2 人事件。
6. 查看真实过滤摘要和候选推荐理由。
7. 选择一名候选人。
8. 将月工时上限从 180 调至 170 并生成新版本。
9. 再次确认原候选人，验证校验失败和自动重新推荐。
10. 确认新候选人并查看成本公式和调剂记录。
11. 立即运行规则优化分析。
12. 采纳一条优化建议并生成规则新版本。

## 技术选型

- Node.js 原生 HTTP：依赖少，部署稳定。
- SQLite：MVP 数据真实持久化、事务简单、便于一键重置。
- 原生 HTML/CSS/JavaScript：无需前端构建，降低比赛和 Render 风险。
- Gaia Responses API：复用公司内部 `OPENAI_BASE_URL`、`CODEX_API_KEY`、`OPENAI_MODEL`。
- Node.js 内置测试：覆盖确定性逻辑、API 契约和闭环流程。

## 风险和挑战

- 公司模型网关可能不完全支持官方 Responses API 的全部严格结构输出字段，需要适配实际响应。
- Render 免费实例 SQLite 位于临时文件系统，部署重启可能重置数据；比赛通过一键重置和固定种子保障可控，但不作为生产持久化方案。
- 规则变化与重新推荐必须保持事务和状态一致，避免重复调剂。
- 模型推荐理由可能出现数字幻觉，必须由服务端抽取数字并校验。
- UI 信息量较大，需要默认展示业务摘要，将技术证据放入可展开详情。
